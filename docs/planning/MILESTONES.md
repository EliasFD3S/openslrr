# Milestones (draft for refinement)

Drafted 12 November 2026 from `main` at `b907b6b`, the native audit
(then 329 bodies, 4 no-ops, 43 missing of 376; on 20 November 2026: 358, 3
and 15), issues #15–#19 and the
roadmap in [scripting/natives.md](../scripting/natives.md#roadmap). Evidence for each
item is in [KNOWLEDGE_BASE.md](../core/KNOWLEDGE_BASE.md) and
[EXTERNAL_RESEARCH.md](../research/EXTERNAL_RESEARCH.md). This is a proposal: order,
scope and exit criteria are open to the maintainers. Status on 20 November
2026: issues #15–#19, #56 and #64 are closed, and each milestone below marks
what has since landed.

Every item starts by checking whether SLRR_rev already implements it and
migrating it when it does ([EXTERNAL_RESEARCH.md §7](../research/EXTERNAL_RESEARCH.md#7-migrating-mechanics-from-slrr_rev)
maps the current gaps). Every milestone ends with the same two checks,
reported separately: the Release x64 build, and an in-game validation of the
named scenario.

## M0 — Reproducible build and verification baseline

Goal: a fresh clone builds, and every claim about progress can be
regenerated.

- Done: track `tools/compile_game_sources.cpp` with a narrow `.gitignore`
  exception, restoring the declared compiler target for clean checkouts.
- Done: `scripts/render_native_coverage.py` regenerates the coverage figures,
  the README chart and table from `src/` and the pinned stock table
  `assets/progress/stock-natives.json`.
- Fix the malformed last `.gitignore` line, and correct the stale statements
  listed in [KNOWLEDGE_BASE.md §9](../core/KNOWLEDGE_BASE.md#9-where-the-documentation-disagrees-with-the-code).
- Partly done: `main` now has standalone regression suites
  (`scripts/run_save_io_tests.ps1 -Suite <name>`) and one CTest target,
  `audio_recovery` (`-DBUILD_TESTING=ON`). No CI workflow exists yet.
- Keep `scripts/check_knowledge_refs.py` passing.

Done when: a clean clone configures and builds `slrr_host` with the README
steps, the coverage figures are regenerated by a tracked tool, and the
knowledge-base check passes.

Question for refinement: should CI run the existing suites, and in what form?

## M1 — Playable Test Track drive

Goal: one stock car drives the Test Track with validated input, HUD and
plausible acceleration.

- #15 HUD size and alignment: done (PR #20 merged).
- Steering, brake, clutch, shifting and the input profile validated through
  a relaunch, on keyboard and a physical pad (scripting/natives.md roadmap step 1).
- Nitro activation and consumption connected to driving.
- Compare acceleration, braking and shifts with the original-game telemetry
  corpus (Baiern, Nonus, Einvagen, Duhen) at two or more frame rates.
- Settle the dyno disagreement (final table endpoint, nitro argument)
  against the MWM binary, not against SLRR_rev.
- Wall collision, impact damage and mileage currently run only for the
  player-controlled car with an engine
  (`src/resources/part_runtime.cpp:sim_step_car`); uncontrolled or
  engineless cars never hit walls. This also matters for M2 and M4.

Done when: the Baiern drives a lap on keyboard and pad, its 0–100 km/h time
is within an agreed tolerance of the original game's at 60 and 144 FPS, and
the HUD matches the reviewed screenshots. The published 6.1 s figure comes
from Steam build 940; an MWM capture should confirm it first.

## M2 — World collision and repair

Goal: the car collides with placed world objects, and garage repair restores
a damaged car.

- #16: keep CFG `body` shapes (box, sphere, rod, mesh, `nocollision`) for
  map placements and build a static collider index independent of render
  culling and LOD. Use a volume test so 0.1 m tree trunks cannot pass
  between probes. A plan is posted on the issue and awaits approval.
- Done: the `PhysicsRef` natives are bound and `GameRef.setActiveCollision`
  is real (#16).
- Extend `GameRef.setState` beyond cars to generic dynamic objects.
- #17: add the native `repair` part command that stock `Part.repair()`
  sends, restoring deformation, slot damage, wheel damage and detached
  panels for the repaired subtree. A plan is posted on the issue.
- Connect impact wear to parts and the regional HUD damage display.

Done when: in Valo City the car stops against trees, lamp posts and
containers at low and high speed; a crashed car leaves the garage repair
visually restored; FPS does not regress.

## M3 — City performance

Goal: driving through Valo City stays well above 60 FPS with VSync off,
with buildings and nearby trees drawn and the far plane at 3 km (#18).

- Measure first: CPU time per phase (scripts, physics, scene collection,
  submission) before and after each change.
- Build the scene instance list once per frame and reuse it for the main
  view, reflections and shadows; cache world matrices instead of
  recomputing every parent chain with an allocation.
- Instance alpha-cutout trees, pool identical materials and share one GPU
  texture per DDS (SLRR_rev measured large reductions from the last two).
- Remove per-frame linear scans (`gameref_find_live`, native alias lookup)
  where the profile shows them.

Done when: the #18 route meets the issue's criteria, with Before and After
metrics and no visual regression.

## M4 — Navigation, traffic and pedestrians

Goal: routes, traffic and pedestrians come from the map data and the stock
natives.

- Done: the city road network is loaded and the `GroundRef` route queries
  (`getNearestCross`, `getRouteLength`, `alignToRoad`, `getStartDirection`),
  `RenderRef.plotRoute` and the traffic natives are bound
  ([world/traffic-races.md](../world/traffic-races.md)). Still to verify in a
  race: the map, rear view and cruise control.
- #19 (closed): pedestrians walk the sidewalk rows and `pedestrianDistance`
  is bound. Open: pedestrians do not use the road graph.
- Traffic behaviour, pursuit and contact limitations listed in
  [world/traffic-races.md](../world/traffic-races.md).
- Water (`setWater`, `addWaterLimit`): still unbound.

Done when: a city race shows a correct route and GPS, traffic follows lanes
and lights, and pedestrians stay off the roadway.

## M5 — Garage and career loop

Goal: a career can buy, tune, paint, repair, race, save and reload a car.

- `Painter` natives (`doPaint`, `paintPart`, `xPaint`) and decal
  persistence through saves: bound with an SDAT texture blob (#64); a
  painted car still needs an end-to-end career save/reload validation.
- `ParticleSystem` natives (nine signatures: bound in #454), flares,
  `GroundRef.setFog` read by the renderer, and part loop sounds
  (`Part.setSfxLoopParams`).
- End-to-end validation: purchase, installed parts, paint and condition
  survive a career save and reload; the preview car never becomes the
  career car.
- Save durability: the stock scripts delete saves before writing their
  replacement and `File.close` cannot report failure.

Done when: a scripted career session survives save, quit and reload with
identical car state and money.

## M6 — Robustness and platform

Goal: malformed data and long sessions cannot crash or damage the
installation. Can run alongside the others.

- Open review risks: DirectShow frame copy bounds, TUFA and RPK count
  checks, file-root confinement and `File.delete`, TREE integer semantics and
  the missing remainder operator, the duplicate Splash enter, retained OSD
  widgets, XInput fallback.
- Display-mode enumeration and controller options documented and validated.
- Optional: crash logging, native call reports and physics telemetry, all
  designed on the PR #3 branch.

Done when: each listed risk is fixed or explicitly accepted, with a note in
the knowledge base.

## M7 — Multicore frame

Goal: when the host thread limits the frame rate, the work of one frame is
spread over the cores. Script semantics, simulation results and the drawn
image must not change.

State after #56: loading uses every core (ENGINE_CONTRACT §6), and the frame
loop still runs on the host thread. In the Valo City drive the host thread
spends about 4–7 ms per frame: scene collection 1–2 ms, physics 1–1.5 ms,
scripts under 1 ms, and draw submission 1.5–2 ms for the world, shadow,
reflection and OSD views. On the 20-thread development machine the GPU took
3–12 ms per frame in the same runs, so splitting this work would not show
there. Each step below is its own PR, with `--perf-log` Before/After rows and
the fixed-step drive.

1. **Measure where the CPU limits.** Run the benchmark with the process
   restricted to 2 and 4 cores (`run.ps1 -Affinity`, or `start /affinity`)
   and on a low-end CPU. Find which zone stops scaling. Also isolate the
   20–60 ms `part_physics_advance` frames that occur every few seconds in the
   drive. They are the visible stutter, and threading is not their known
   cause.
2. **Scene collection in parallel.** `scene_instances_collect` and
   `scene_instances_collect_batches` cull the 64 m prop cells. Split the cells
   over the pool; each job culls its cells and builds its own instance and
   batch lists, and the lists are appended in cell order so draw order stays
   the same. Prerequisites:
   - `geometry()` must not insert during the batch. Load missing meshes
     before the batch with the existing `preload_meshes` and leave lookups
     read-only.
   - The HiZ test (`LibBgfxBackend::hiz_visible`) only reads members set
     before collection, so jobs can call it.
   - Pedestrian palettes (`complete_skin`) are per walker; build them in a
     second batch once the visible walkers are known.
3. **Draw submission from several threads.** bgfx records draws from worker
   threads through encoders (`bgfx::begin`/`bgfx::end`, up to
   `Init::limits.maxEncoders`, default 8). Record the shadow cascades, the
   reflection faces and the world view from separate jobs. To do this,
   change the draw helpers in `bgfx_lighting.cpp`, `bgfx_shadows.cpp` and
   `bgfx_osd.cpp` from the global `bgfx::` calls to an `Encoder*`, and set
   uniforms per encoder. View sort modes keep the order within each view.
   The OSD stays on the host thread because it reads script widgets.
4. **Physics, after PR #48 settles the vehicle model.** Per tick, advance
   each car (`advance_chassis_tick`) and each awake loose body in parallel
   against the read-only static scene. Then exchange contact impulses in a
   serial phase, in a fixed order, so results do not depend on the thread
   count. This only pays off with several simulated cars (traffic, M4).
5. **Pipelined frames (optional, needs maintainer approval).** Prepare frame N
   for rendering (collection and submission) on a second thread while
   scripts and physics run frame N+1. Build it from a snapshot of the
   render-visible state: instances, cameras, lights and OSD. This changes
   module responsibilities, because GameRef state would be read off the host
   thread, so it needs agreement before code.

Not planned: running script threads in parallel. Stock scripts rely on
cooperative scheduling, and parallel Java would break them (ENGINE_CONTRACT
§6).

Done when: with the process limited to 4 cores, the city drive's host-thread
time per frame drops by an agreed amount. The fixed-step drive must keep the
same draw counts and matching window captures, and the knowledge base must
document each new parallel stage.
